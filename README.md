
## 🎯 سناریوی مسابقه 
تیم توسعه، ساختار اولیه کد را ارائه داده است، اما عملیاتی‌سازی و استقرار کاملاً بر عهده شماست.
ورودی شما به این صورت است که یک کد api به زبان go نوشته شده است و یک static page برای UI آن در نظر گرفته شده است این پروژه ابزاری تحت توسعه است که با redis و postgresql کار میکند.
ابتدا به روش بخش بندی هایی که پایین تر نوشته شده است اقدام به مستقر کردن application و عملیاتی سازی آن کنید. بعد از آن روی سناریوی زیر باید کار شود.
انتظار شما این است که ارتباط api با redis و postgresql به این صورت باشد که redis‌ حافظه موقت در ram است و زمانی که اپلیکیشن را اجرا می کنید این امکان را دارید که اطلاعاتی شامل نام و وضعیت تاهل و .. را وارد کنید و انتظار این است که این اطلاعات داخل redis و postgresql ذخیره شود و زمان get کردن آنها کد api ابتدا تلاش میکند از redis‌ اطلاعات را بگیرد و در صورتی که موفق نشد اقدام به گرفتن اطلاعات از postgresql کند و ذحیره سازی در redis را مجددا انجام دهد تا برای استفاده های بعدی data داخل ram در دسترس باشد. در این پروسه اشکالی وجود دارد که بعد از پیاده سازی نهایی پروژه نیاز است که آن اشکال پیدا شود و راهکار موقتی برای رفع آن پیشنهاد شود. همچنین دو function در کد تعبیه شده که نیاز است از طریق لاگ و مانیتورینگ تشخیص داده شود که این فانکشنها مستقلا چه کاری می کنند و چه مشکلی را در سیستم بوجود می آورند.
## 📁 ساختار پروژه
```

project-structure/
├── src/ # کدهای اصلی اپلیکیشن
│ ├── api/ # سرویس backend به زبان Go
│ └── ui/ # فایل‌های استاتیک فرانت‌اند
├── backup/ # پیکربندی backup (توسط شما تکمیل شود)
├── monitoring/ # پیکربندی مانیتورینگ (توسط شما تکمیل شود)
├── nginx/ # کانفیگ‌های Nginx (توسط شما تکمیل شود)
├── pipelines/ # پیکربندی CI/CD (توسط شما تکمیل شود)
└── scripts/ # اسکریپت‌های کمکی (توسط شما تکمیل شود)
```


## 🛠️ وظایف مورد انتظار

### بخش ۱: Dockerize کردن پروژه 🐳

#### ۱-۱  Dockerfile برای API (Backend)
- از **multi-stage build** استفاده کنید
- از **base imageهای رسمی و سبک** استفاده کنید
- **best practiceهای امنیتی**  را رعایت کنید
- فایل `Dockerfile` در مسیر `src/api/` ایجاد شود
- پورت api پورت ۸۰۹۰ است.

#### ۱-۲  Dockerfile برای UI (Frontend)
- از image رسمی `nginx:alpine` طوری استفاده کنید که فایلهای static را serve‌ کند.
- فایل `Dockerfile` در مسیر `src/ui/` ایجاد شود
- نکته ای که در این بخش وجود دارد این است که برای تغییر متغیرهای محیطی ui می توان از فایل config.js داخل مسیر ui استفاده کرد
- پورت ui پورت ۸۰۸۰ است.

#### ۱-۳  Docker Compose 
 بعد از آماده سازی docker file ها اقدام به ساخت docker compose کنید. همچنین نیاز است که redis و postgresql را نیز با کمک آن بالا بیاورید. 
- سرویس‌های زیر را تعریف کنید:
  - `api` (build از Dockerfile)
  - `ui` (build از Dockerfile) 
  - `redis` (از image رسمی)
  - `postgres` (از image رسمی)

**کد بک اند پروژه جهت اتصال به postgresql و redis از env varهای زیر استفاده می کند**

```

REDIS_HOST:
REDIS_PORT:
POSTGRES_HOST:
POSTGRES_PORT:
POSTGRES_USER:
POSTGRES_PASSWORD:
POSTGRES_DB:
```
انتظار می رود با ریبوت شدن سیستم عامل کلیه کانتینرها به صورت خودکار اقدام به فعالیت مجدد کنند.


### بخش ۲: آماده سازی nginx 🌐 :

#### ۲-۱  installation
اقدام به نصب nginx به عنوان یک سرویس لینوکسی (بدون استفاده از داکر) کنید. 
اسکریپت نصب را داخل فولدر قرار دهید
#### ۲-۲  reverse proxy
طوری nginx را کانفیگ کنید که به عنوان reverse proxy برای api و ui کار کند. (ui را قبل تر پشت nginx در لایه داکر قرار دادید و انتظار می رود که این واسط کاربری از بیرون سرور صرفا از طریق nginx اصلی که روی سیستم نصب میکنید در دسترس باشد) 
#### ۲-۳  caching
برای api کش تخصیص ندهید. برای UI سیستم کشینگ فعال باشد. این cache باید از ram سیستم استفاده کند و نباید بیش از ۲۰۰ مگابایت ذخیره سازی انجام دهد.اطلاعاتی که بیش از ۲۴ ساعت در دسترس نبودند نباید کش آنها باقی بماند. روشی برای حذف فایلهای cache طراحی شود ( یا از طریق کال کردن یک api توسط کاربر ایجاد شود یا اینکه هفته ای یک مرتبه به صورت خودکار اقدام به حذف کلیه فایلهای cache شود.)
#### ۲-۴  compression
وب سرور باید compression انجام دهد. اطلاعاتی که فشرده میشوند نباید کمتر از ۱۰۲۴ بایت باشند. 

#### ۲-۵  secuirty
جهت امن سازی nginx انتظار می رود که از xss attackها و حملات clickjacking جلوگیری شود همچنین دسترسی به دوربین و میکروفون و لوکیشن کاربر نیز محدود شود.

### بخش ۳: آماده سازی pipeline ⚡ :
محل ذخیره سازی imageها داخل سروری است که در اختیار شما قرار داده شده در واقع نیاز نیست خروجی build‌ جایی غیر از سرور push شود.همین که در لیست imageهای سرور برای استفاده قرار بگیرد کافی است ضمن اینکه همین سرور نقش runner را به عنوان یک shell exec ایفا می کند و قبلا فایل config.toml روی سرور آماده شده است و اتصال برقرار شده.

#### ۳-۱  build
هر بخش Pipeline باید یک template جدا باشد و اساسا Pipeline ساختار داشته باشد و همگی از طریق فایل .gitlab-ci.yml صدا زده شوند.
باید دارای دو استیج build و deploy باشد.
داخل استیج build باید build برای ui و api به صورت دو job جدا باشد.
همچنین trigger تمامی job ها باید روی برنچ main در مسیر های pipeline ها و مسیر مربوط به خود source کد باشد. 
در هنگام build تگ آن باید sha کوتاه شده کامیت بر روی source code باشد

#### ۳-۲  deploy
داخل استیج deploy باید deploy برای ui و api به صورت دو job جدا باشد و پس از success بودن build های مربوط به خودشان trigger آنها انجام شود. در واقع به روش continous deployment عملیات deploy صورت پذیرد.
در قسمت api باید user و password پایگاه داده به عنوان variable در gitlab تعریف شود و pipeline جهت مقدار دهی env varهای compose از این متغیرها استفاده کند.

### بخش ۴: آماده سازی monitoring 📊 :
#### ۴-۱  prometheus
در سطح ماشین اقدام به بالا آوردن یک نود prometheus شود. در کانفیگ prometheus از discovery کانفیگ جهت اضافه کردن targetها استفاده شود.
#### ۴-۲  gathering
اطلاعات مهم متریکهای کلیه کانتینرها (خصوصا متریکهای redis) و خود مانشین host نیاز است که جمع آوری شود.
#### ۴-۳  alert manager
به نحوی alert manager‌ کانفیگ شود که در صورتی که redis افتاد alerting داشته باشیم. نیاز نیست که این alertها به جایی ارسال شوند. نکته نهایی اینکه در صورتی که از یک موضوع مشخص severityهای سطح بالاتری وجود داشت inhibition رعایت شود.

### بخش ۵: آماده سازی backup/restore 💾 :
#### ۵  backup/restore automation
از ansible برای ایجاد backup/restore automation استفاده شود. حتما از role استفاده شود و roleهای backup و restore را داشته باشیم.
از فایل inventory.ini و host_vars برای تعریف host ها استفاده شود.
تمامی مقادیری که باید در فرایند backup و restore تغییر کند به صورت vars داخل role های مربوطه تعریف شود.
امکان اجرای role های backup و restore با استفاده از تگ بر روی playbook امکان پذیر باشد. error handling مناسب وجود داشته باشد.
از Best practiceهای موجود استفاده شود.
